# X650 无机械臂：起飞、短时定高与降落验证

2026-10-30：用户将当前优先级改为先完成飞机本体的起降和稳定飞行。现场为室内，有熟悉 PX4 多旋翼的飞手；无机械臂 X650，装电池约 3.02 kg，四片桨仍拆下。动捕尚未恢复，机械臂未接。**本阶段采用 PX4 自带控制器，由现场飞手操作；当前工作是准备与只读检查，尚未进行首飞。**

配套执行准备：[POWER独立供电验证](X650_POWER_VALIDATION.md)、[首飞参数与最新决定](X650_FIRST_FLIGHT_PARAMETERS.md)。后续COM13已恢复，已完成独立供电60.078秒实机观察：USB无效、POWER1有效、5V总线5.094–5.108V，未发现重启／过流、输出全零。用户确认电池约24.4V与实际一致。用户随后决定保留原操纵范围与 SA 档位；临时改动的三项已按备份恢复，108项清单一致。未预先备份的自主上升联动项 `MPC_Z_V_AUTO_UP=1` 经用户确认暂留，见[恢复记录](validation/px4_first_flight_modes_20261030/README.md)。供电型号、电流／剩余电量标定和实际飞行仍未验证。

## 当前能做什么

Pixhawk 6X Pro 内置 IMU、气压计和 BMM150 磁力计，提供两个外接 GPS 接口，没有内置 GNSS 定位接收机。接口或 `SYS_HAS_GPS=1` 不代表已有可用 GPS。[厂家规格](https://docs.holybro.com/autopilot/pixhawk-6x-pro/technical-specification)

室内没有可用动捕、VIO 或其他水平定位时，可以在合适的试飞场地，由有经验的飞手验证 Altitude（定高）模式的人工起飞、短时飞行和降落。定高模式控制姿态和高度，横向位置由飞手持续修正；松杆不会主动刹停并锁住水平位置。因此这一阶段不验收自动定点悬停、位置精度或自动航线。[PX4 定高模式](https://docs.px4.io/main/en/flight_modes_mc/altitude)

这里的“室内”须由现场飞手确认是有足够漂移、制动和降落余量的试飞区域，人员与旋翼活动范围隔离；不能因为有飞手就把普通办公房间视为可飞场地。首轮的起降位置、活动边界和提前降落条件应在装桨前确定。[PX4 首飞指导](https://docs.px4.io/main/en/flying/first_flight_guidelines)

## 分阶段测试安排

### 1. 飞行供电与地面记录，继续拆桨

确认已安装电源模块的型号、与 6S 的兼容性及 POWER1/POWER2 接法。合适模块提供飞控所需的稳压低压供电；**不能把 6S 原始电压直接送到飞控 POWER 低压针脚**。6X Pro 的常规 POWER 输入为约 5 V，飞控也可被 USB 供电，二者要区分。[供电说明](https://docs.px4.io/main/en/flight_controller/pixhawk6x_pro)

在后续明确的拆桨、锁定状态下，由现场人员接通实际飞行电池，记录 POWER 有效位、5 V、电池电压、串数、告警和运行时间，再验证撤掉 USB 供电后飞控与接收机能稳定工作。电压与独立仪表交叉核对；电流比例在有已知参考时再标定，不把 ESC 遥测数值自动当真值。

确认飞控 SD 卡能产生并读回 ULog，检查无复位／新故障。后续飞行依靠机载 ULog；电脑上的 Debug 线、外部供电线等台架牵线应在装桨试飞前移开。NX 是否随飞机保留按实际构型记录；本阶段没有控制发送任务，也不增加 NX 系统配置或日志。

### 2. 准备首飞配置，并在拆桨状态下复核

用户选择沿用原配置。三项临时改动已按备份恢复；不再执行收紧包线或重映射提案。只对新的明确问题作针对性处理，不把历史提案当作首飞的必经程序。

| 配置项 | 计划处理 |
|---|---|
| SA 模式 | 保留上档 Altitude、中档 Position、下档 Offboard；当前人工首飞只使用上档，不再增加重映射及逐档重测 |
| SF／SB | 保持已有解锁／锁定和紧急停机功能；确认重启后的实际标志，不只看拨杆位置。SB 停机用于紧急中止，不能当作正常降落 |
| 飞行包线 | 保留手动倾角35°、偏航150°/s、上升3 m/s、下降1.5 m/s；它们是上限而非要求飞手满杆。现场飞手按场地操作，不继续收紧配置 |
| 失联／低电 | 按无水平定位情形核对实际降级路径、延时和电池告警；不依赖不可用的返航或定点。当前低电动作及台架安全旁路也须纳入逐项审查 |
| 姿态／角速度 PID | 从当前 PX4 参数和机械检查出发，暂不盲目提高增益；仿真 PID 不直接视为真机最优参数 |
| 校准 | 保留已恢复的校准。机架方向、姿态显示与实际动作一致性及上电后的 IMU／罗盘状态仍需检查 |

当前已读到 `MPC_TKO_SPEED=1.5`、`MPC_LAND_SPEED=0.7`、`MPC_Z_VEL_MAX_UP=3`、`MPC_Z_VEL_MAX_DN=1.5`（m/s），`MPC_THR_HOVER=0.5`、`MPC_USE_HTE=1`；这些是记录到的配置，**不是本计划推荐值，也不表示它们在每个模式下都直接决定动作**。PX4 的 `MPC_` 参数前缀表示 Multicopter Position Control，与项目研究的模型预测控制 MPC 不是同一含义。

复核模式、方向、独立供电、预检和 ULog 后，再进入装桨准备。此前已验收的遥控和电机测试不整套重跑；只有接线、映射或相关配置发生变化的部分才重新验证。解除 SB 后的预检必须在该轮真实初始条件下通过；不跳过预检、强制解锁或伪造定位。

### 3. 飞手完成首次短时定高起降

现场飞手核对实际无臂配置、重心、紧固件、飞控安装和四片桨的型号／正反／旋向匹配，并在已确认的试飞区操作。已验证的俯视电机映射为：M1 右前逆时针、M2 左后逆时针、M3 左前顺时针、M4 右后顺时针；桨叶安装还须单独核对产生向上升力的方向。

计划先进行一次短时人工起飞—定高保持—缓慢降落，观察窗口约 10–20 秒，具体高度与时长由现场飞手按场地和响应决定。飞手负责水平位置；发现明显振荡、不可控偏移、推力异常或供电／估计器故障时提前结束。本计划不通过聊天、网页按钮或远端命令发动首飞。

首次不安排空中失联、空中停机、自动调参或大幅机动。正常降落由飞手控制下降、落稳、确认锁定与停转；SB 切断推力会使空中飞机失去升力，不能用来代替降落。

### 4. 每次落地读日志，再决定是否调参

保存参数快照、固件标识、飞行构型／质量、电池、场地与飞手观察，以及对应 ULog 和视频。所有分析结果保存在电脑，NX 不保存实验日志。

| 检查对象 | 主要证据 | 下一步 |
|---|---|---|
| 姿态／角速度 | 实际值与设定值、持续振荡、相位滞后、电机饱和 | 先排机械／桨／振动问题，再按 PX4 方法逐轴调整，不把所有误差归咎于 P |
| 垂直控制 | 高度／垂向速度与目标、悬停推力估计、起飞跃升或下沉 | 检查高度估计、推力模型及垂直环，依据带桨记录调整 |
| 传感器与供电 | IMU clipping／振动、估计器切换／偏置、电池与 5 V、复位事件 | 出现异常先修复，不以延长试飞代替诊断 |
| 落地 | ground_contact／landed、锁定时刻、落地后转速和飞手观察 | 确认完整起降过程，不只评价中间悬停片段 |
| 记录本身 | 时间连续性、主题覆盖、丢失记录与文件可读性 | 缺失证据时明确标记“未验证” |

第一轮不凭室内无定位的 x/y 数值报告厘米级悬停精度。成功标准是可控起飞、短时无持续发散／显著振荡、飞手能控制漂移并正常降落；这些通过后，再逐步延长持续时间并重复。阈值应结合实际日志噪声、场地和飞手判断确定，不能提前把未测阈值写成已通过。

## 何时回到原 MPC

先取得飞机本体的可重复起降、姿态和定高基线，再恢复有效水平定位（优先等现有动捕；其他方案需独立接入验证）。随后才能做真实状态影子运行、位置目标内部回读与受限位置闭环。

原全身 MPC 不能直接在缺少关节反馈时填零运行。若阶段性采用无臂 MPC，需要显式的无臂模型、输入与约束配置，并完成独立离线／仿真验证。当前优先级是飞起来与可靠降落，这一算法分支尚未实施。

## 只读工具与证据路径

- `scripts/px4_first_flight_readonly.py`：固定白名单、未解锁／零输出守卫、前后状态记录；不写参数、切模式、解锁、校准或控制电机。不访问 NX。
- `tests/unit/test_px4_first_flight_readonly.py`：16 项软件检查通过，覆盖非法命令、缺失／过期定位、异常状态、记录保留与串口释放。
- `artifacts/px4_first_flight_20261030/inventory_v1/`：电脑上完整报告及原始串口记录；仓库摘要以 SHA256 关联，采集成功不等价于首飞许可。

在已确认的拆桨、锁定、零输出台架条件下，独占 COM13，从仓库根目录采集到新的目录：

```powershell
python -B scripts/px4_first_flight_readonly.py --port COM13 --output artifacts/px4_first_flight_<新的编号>/inventory
```

输出固定保持 `flight_ready=false`；它有意不把软件状态替代现场放行决定。若设备固件变化、读数失效或状态异常，先分析原因，不通过放宽守卫继续。
