# Orin NX 处理器在环与部署前调试

本流程承接 ABI 4 的同输入计算测试，使用 X650＋二连杆、TS20-50/24 V 条件模型及现有上层 MPC。NX 只运行 C++ 程序；输入、原始结果和日志保存在工作站，构建临时目录使用 NX 的 `/dev/shm`，完成后清理。整个流程不创建实机执行器发布者，不等价于无桨台架或飞行验收。

## 已实现的边界

`control_packages/x650_wholebody_v1/pil` 提供持久 C++ 进程，通过有界、长度前缀帧收发消息。SSH 只建立一次，不在每个周期新建进程。适配器链接已有 ABI 4 Core、ABI 2 优化器和 TS20 预测库，并核对实际加载 ELF 的 SHA。正常运行由一次真实或已记录的 `LiveStart` 初始化，随后连续保留 Core Memory；不逐条恢复历史 Memory，不从外部加载每周期的最优解。

状态解码、参考轨迹、实际关节命令与 MIT 包历史、QP/非线性/保持检查继续复用生产 C++ 实现。每次响应绑定完整请求 SHA、session、epoch、序号、原始 issue 时间和配置身份；错误锁存后不再返回可执行候选。重启必须重新初始化，执行端仍须使用新的会话身份并拒绝旧会话响应。

记录流工具与实际仿真分开。新增 `x650_nx_sync_pil_v1` 场景将真实 PX4/Gazebo 反馈送入 NX，再把 NX 候选发给原执行端。它使用明确的暂停／步进协议，只有新的完整运行和独立审计才能建立物理闭环结论。Python 工作站负责字节中转，服务器 Python 负责同步试验编排；不能据此宣称已有经过验收的 C++ 实时网络网关。

## 时钟与耗时

服务器和 NX 的 monotonic 时间没有共同原点。服务器用自己的时钟保留原始状态 issue、发送和接收；NX 用自己的时钟计算接收、Core 起止和服务阶段耗时。两台机器的绝对时间戳不得相减。

| 指标 | 测量方式 | 含义 |
|---|---|---|
| NX Core wall / thread CPU | NX 内部包住 `Core::step` | 完整矩阵、QP、候选检查；不含传输和 JSON |
| NX 服务阶段 | NX 完整请求收齐到响应对象准备完成 | 包含解码、检查和结果构造；不含最终响应序列化及发送 |
| 端到端往返 | 发起端同一 monotonic 时钟 | 包含请求发送、中转、排队、NX 处理及响应返回 |
| 服务阶段以外时间 | 往返减 NX 服务阶段 | 包含传输、SSH、主机调度和输出序列化；不能称为纯网络延迟 |

在墙钟实时方案中，服务器必须独立保留原 issue 的 50 ms 求解准入期限。NX 内部将输入 issue 映射至本地接收时刻，只用于同机计算检查；**不能给服务器的旧输入续期**。20 ms 下发、160 ms 原始指令有效期、100 ms 最大模型 dt、关节消费进度监督继续由服务器执行端负责。重复下发不更新原始有效期，网络连通或心跳正常不代表控制状态新鲜。

用户选定的同步仿真方案单独声明 `synchronous_simulation_only=true`：服务器保留原始 issue 和往返数据，等待响应期间检查 Gazebo 时间完全不前进，采用 3 秒墙钟通信故障上限；NX 内部 50 ms 准入、QP 与保持约束不变。物理步长 4 ms，执行间隔 20 ms，求解间隔 40 ms，后两者都以仿真时间计算。它不继承墙钟实时资格。

实际连接前还需实现 C++ 服务器桥：原始快照入账 → NX 通信线程 → 原始 issue 的期限及身份检查 → 现有独立 50 Hz 下发器。必须沿用“上一候选已首次实际发送”准入语义，不能把 NX 计算完成当作关节实际执行。工作站的 `validate_candidate` 是这项接口的测试参考，不是生产执行端的替代品。

以上 C++ 桥属于后续墙钟实时方案。当前同步场景在启动和起飞前完成 Gazebo 服务发现；在接管边界暂停物理、收齐真实反馈、结束旧下发者的预发送，再初始化 NX。每次步进检查确切仿真时间；每次下发后用下一段物理日志核验两个关节的消费时间与指令值。试验退出先确认零关节指令被消费，再恢复物理推进，交回原降落流程。NX 不拥有 ROS 或实机执行器。

## 验证顺序和通过条件

1. **连续记录流。** 用完整历史物理状态输入，NX 一次初始化、连续求解；独立核验全部输出、Memory 步数与原始命令链。当前四组共 2420 条，记录中的受扰性能失败也保留。参考状态不会随新命令变化，因此这项测试不是物理闭环。
2. **故障注入。** 重复和乱序序号、旧 epoch、错误配置、过期关节状态、错误 dt、非正交姿态、越限、非有限输入、截断帧、断开、空闲超时及重启；核验故障锁存、无有效候选、事务性状态保持。另测原 issue 到结果的 50 ms 边界与 PVA 重构。
3. **真实通信路径。** 从服务器经受限 loopback SSH 隧道请求真实 NX。保持所有慢样本，分别报告 Core 与往返。阶段 1 的延迟观测不能替代该测试。
4. **同步时钟探测。** 用户选定的同步方案先在不解锁的实际 PX4/Gazebo 上验证暂停、精确步进和恢复；确认等待 NX 时两个仿真时钟同时冻结。单独的实际反馈影子通道仍是后续墙钟实时方案的准备项目，不声称本轮已完成。
5. **新的完整末端保持。** 只有网络/桥接方式满足明确的测试时钟契约后，才切换到 NX 候选。仍须验收实际关节消费、PX4 编码、超时移交、降落停桨和参数恢复。随后普通八字，再快速八字。
6. **真机接口台架。** 独立验证动捕时间戳、坐标变换、TS20 实际总线和功率条件、硬件看门狗、断流/重启以及执行器响应。仿真和 NX 计算测试均不能代替该阶段。

如果公网链路不能满足期限，应选择以下一种明确的下一阶段，不应扩大期限来掩盖问题：

- **同步仿真时间 PIL**：在受控物理步边界等待 NX 结果，以仿真时间推进被控对象。它验证算法和反馈闭环，网络等待单独记录；不得把它报告成 25 Hz 墙钟实时闭环或用其证明 Offboard 看门狗。
- **有线局域网实时 PIL**：让运行仿真的 Linux 主机与 NX 位于同一有线局域网，使用 C++ 传输/执行适配层；再按原墙钟门限验收完整闭环。NX 仍只运行控制代码。

## 复现工具

- `scripts/prepare_x650_pil.py --output <新的工作站目录>`：校验原始归档，生成连续记录流、协议与代码包。原始数学源和 wire 格式仍核验字节身份；参考值比较器的有意修复单独保留修改前后 SHA，不继承旧接口资格。
- `scripts/build_x650_pil_in_ram.py`：通过 SSH 的 stdin 输入代码 tar，链接指定已有运行库。NX 默认 RAM 构建，仅留下一个可执行文件。服务器 `/dev/shm` 为 noexec 时，可显式使用服务器数据盘临时目录；结束后清理。
- `scripts/run_x650_pil_stream.py --help`：连续记录流、完整响应、误差及耗时统计；`--paced` 按原记录 dt 在工作站节拍发送，但不会使记录流变为物理闭环。
- `scripts/test_x650_pil_faults.py --help`：实际 NX 进程故障与独立发起端准入测试。
- `scripts/probe_x650_pil_path.py --help`：绑定 `127.0.0.1` 的 SSH 反向隧道；测试后关闭隧道和所属 NX 进程。不开放公网控制端口。
- `tests/unit/test_x650_pil_transport.py`：发起端时钟分离、准入边界、指令完整性测试。
- `control_packages/x650_wholebody_v1/pil/test_reference.cpp`：舍入容差内参考值通过，超过容差及 NaN/Inf 被拒绝。
- `control_packages/x650_wholebody_v1/pil/simulation_stepper.cpp`：服务器上的 Gazebo 暂停／精确步进工具；异常断开时不擅自恢复物理。
- `scripts/probe_x650_sync_clock.py`：不解锁地验证 Gazebo 时间与 PX4 IMU 时间戳同时冻结、精确步进和恢复。
- `scripts/run_x650_sync_pil.py` 与 `simulations/x650_nx_sync_pil_v1/`：新的实际仿真链路、接管、消费检查和恢复流程。
- `scripts/restore_x650_parameter_journal.py`：保留完整原始记录、确认地面状态后恢复一次未完成的参数事务；不删除未核验的日志。
- `scripts/audit_x650_sync_pil.py`：独立核对 NX 输入输出、真实消费、PX4 ULog、原生末端轨迹、降落和参数事务；输出分开的计算/往返时间序列。
- `scripts/plot_x650_sync_pil.py`：从审计导出的 CSV 画图，先核验时间加权 RMSE 与审计结果一致。
- `scripts/archive_x650_sync_pil.py`：只在仿真关闭后归档完整成功/失败运行，逐成员读回并核对 SHA。

### 同步运行入口

服务器先准备 JSON plan，绑定已有完整保持任务、startup manifest、通过的 PX4/Gazebo 时钟探测报告，以及指定 NX 构建的 source SHA。固定 `physics_tick_ns=4000000`、`solve_ticks=10`、`dispatch_ticks=5`。`case=normal` 还必须绑定新同步保持的完整审计和 launch 文件；工具会核对原始证据及相同控制参数，不能仅修改 `passed` 字段继承旧资格。

在服务器的既有 ROS/PX4 环境中先运行：

```bash
python3 simulations/x650_nx_sync_pil_v1/launch.py \
  --plan <bound-plan.json> --output <new-server-output> --dry-run
```

工作站用 `run_x650_sync_pil.py` 的 `--server-command` 调用相同命令去掉 `--dry-run`，并提供服务器 SSH 与 NX SSH 参数、NX `--build-report`。工具创建仅绑定 loopback 的反向隧道，NX 只在服务器已暂停并请求接管时启动；输入输出经内存流转。日志分别留服务器与工作站。脚本本身提供 `--help`。

飞行流程退出后运行审计，三个路径分别指新物理运行、新 launch 目录和新的审计输出目录：

```bash
python3 scripts/audit_x650_sync_pil.py \
  --run <physical-run> --launch <launch-output> --output <new-audit-output>
```

本轮已完成 30 秒保持和 32 秒普通八字。普通八字运动段为 2–28 秒，完整窗口包含前后保持；两种误差口径同时保留。下一步快速八字须显式扩展同步场景准入并保留本轮通过凭据，当前脚本不会自动启动快速工况。

每次使用新的输出目录，失败与成功均保存。数值一致性、链路时限、连续执行和物理误差是独立结论。任何一项失败都不能被“进程跑完了”覆盖。具体结果见 [2026-10-27 调试记录](validation/orin_pil_20261027/README.md)。
