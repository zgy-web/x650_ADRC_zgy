## 判定口径

以下三类结果必须分开：

- 软件传输测试：实际执行本次编译的 C++ ROS/UDP 程序，但消费端为合成夹具。
- 实际接口分项审计：检查实际 Gazebo 插件消费、PX4 ULog 编码、单一写入者与退出恢复。
  即使这些项目通过，短时退出记录的 `hold_accepted` 仍为 `false`。
- 完整末端保持：原始 30 s 测量窗口、实际执行、参数恢复、独立物理末端、关节自由预测、
  完整记录和全部输入数值复算全部通过后，才能出具阶段通过证据。

普通八字以新执行路径的完整保持为前提；快速八字继续后置。
以前单进程架构的保持通过记录不自动覆盖本次架构。
同样，hold_v15 的历史通过只属于原库和第 7 版执行条件，不能转授给第 8/9 版。

## 普通八字首试与执行协议修订

[`normal_failure_v1.json`](normal_failure_v1.json) 保留了第一次普通八字的失败证据。
有效下发仅覆盖约 3.70 s，185 次计算后退出，不能作为完整轨迹结果。
第 185 轮计算内发生一次 11.531723 ms 的 gen2 GC，总计算为 27.718495 ms，
未赶上下一个周期；上一条命令此时已达 62.887178 ms，超过原 50 ms 期限并被拒绝。
原始回执证实停止零速被消费，飞机已降落上锁，参数已恢复。

协议修订为第 8 版：在 worker 构造及 executor 注册完成后、READY 和参数事务前，
执行一次显式完整 GC，记录启用状态、阈值、冻结对象数、收集数量和耗时。
自然运行期 GC 仍启用，未 freeze、disable 或修改阈值，C++ 数值库和控制参数未改。
该执行层变化重新进入完整保持验收；第 15 次保持是第 7 版的历史通过记录，
不能单独替代第 8 版的验收。

## hold_v16 的 QP 失败及第 9 版候选

第 8 版的 hold_v16 在约 28.38 s、第 1416 次求解时退出，已有 1415 次候选被接受。
这次触发的是原始约束行可行性拒绝，与普通八字首试中的 GC 停顿不同；
接近 30 秒不构成完整保持通过，也不从已完成片段重新挑选窗口。

已定位并复现的数值过程为：

修复属于数值实现变化，因此新 ELF、任务、完整数值证明及后续物理证据必须各自绑定。

## 已定位并修正的问题

| 问题 | 原始证据/后果 | 本次修正 |
|---|---|---|
| 活动参数事务中重新构造工作进程 | 原前置保护拒绝启动 | 起飞前构造，实际接管时一次性注入真实参考和历史 |
| DDS 进程启动但端点未匹配 | 候选/消费通道尚不可用 | 明确检查发布订阅匹配，发现查询和就绪文件写入置于定周期循环之前 |
| 空闲 tick 相位决定首次执行 | 首次候选刚错过周期，初始年龄偏大 | 首个有效候选只锚定一次活动相位，后续不能移动周期 |
| 消费确认与新采样串行等待 | 计算后的等待使候选错过发送周期 | 实际发送通知开放下一计算；上一命令两关节消费仍是下一次发送的必要条件 |
| 墙钟和模型时钟双重 20 ms 最小间隔 | 4 ms 物理网格上 20 ms 被推到 24 ms | 模型更新依据实际仿真源时间；截止时间和输出周期仍依据 monotonic 墙钟 |
| 来源进程持续保留嵌套反馈/ROS 消息 | 第 11 次试跑自然 gen2 GC 约 32.6 ms，来源超期退出 | 来源端仅保留最新消息，完整副本交第二个独立记录进程；降落后重建并核对记录 |
| 仿真并行时计算接近周期预算 | 第 13 次试跑计算 18.7–19.8 ms，来源到候选约 22.3–23.6 ms | 单独测量同输入 CPU 分工方案，将本次仿真后台任务与关键进程分离 |
| 构造对象后运行期首次 gen2 回收 | 普通八字首试第 185 轮发生 11.532 ms GC 并导致旧指令超期 | 第 8 版将显式完整回收放在 READY/起飞前；自然运行期 GC 保留，效果仍需新整窗验收 |
| QP 聚合容差随归一化掩盖原始行违反量 | hold_v16 第 1416 轮被外层 `2e-7` 门限拒绝 | 第 9 版候选增加按行尺度变换的内部收敛条件，须先完成新数值资格化和新物理验收 |

所有年龄限制保留：来源 25 ms、候选从原快照计算的有效期 50 ms、输出周期 20 ms。
没有关闭自然 GC，没有把旧样本重打时间戳，没有调整控制参数来掩盖运行时超期。
退出成功也不会把失败试跑改成保持通过。

**20 ms 是下发周期；50 ms 是从原快照起算的最长指令寿命，并保留为完整计算/模型 dt 上限。**
重复消息不能延长旧命令寿命，一次计算不足 50 ms 也不保证能够赶上有效发送槽。
过期检查发生在下发 tick，不是第 50 ms 瞬间的硬件停止；故障时正常 PVA 停发、关节发送零速，
PX4 暂时保留最后目标，随后由原恢复流程接管。实际真机必须另验总线消费、独立超时和物理停止行为。

## 复现与真机迁移

运行和审计命令见[实际仿真入口](../../../simulations/x650_isolated_live_v1/README.md)，
完整测试层次见[执行隔离及测试方法](../../X650_EXECUTION_ISOLATION_AND_TEST_METHOD.md)。

资源分工属于本次服务器运行配置：来源 CPU 17、算法候选核心组 87/89/91/97、输出 CPU 93、
准入 CPU 94、消费观察 CPU 95；本次自有 Gazebo/记录进程避开这些核心及其 SMT 配对。
单核算法配置曾运行 10.88 s、538 轮，随后计算耗时持续升高并导致过期，未完成保持。
多核心组允许内核选择空闲核心，不宣称隔离了宿主机上的其他任务。
所有进程仍采用普通 Linux 调度，未独占宿主机或改变其他用户进程。
接管前读取每个自有线程的实际 affinity，与声明逐项核对。
更换容器硬件或 Orin NX 后必须重新测量并冻结资源配置，不能把这些 CPU 编号直接搬过去。

本次仿真仍使用来源台架条件下的 TS20 模型；用户的 TS20-50、24 V、实际负载、真实总线与
动捕适配尚需单独验收。服务器完整保持即使通过，也不构成真机或硬实时认证。

特别保留一个未认证的退出边界：上一条普通关节命令仍未确认时发送停止零速，
最新消费观察可能跳过队首计数，导致零速确认不能完成。它可能发生在故障退出，也可能发生在
末条命令仍待确认的正常结束。当前缺少零速回执会使运行不合格；结束新写者后恢复原流程
不等于已证明零速实际被确认。该边界须有专门故障注入和原始总线/物理记录，才可用于真机准入。
